2019 年写过一个 2048，是我的第一个小游戏，现在还挂在项目列表里。

翻了一下代码，方块是一个个 `div`，移动靠 `translate3d`，四个方向各写了一大段逻辑。最高分存在 localStorage 里。很早期的写法，不过还能玩。

这次想用 AI 把它重新做一遍。玩法照旧，换成 Three.js，再加点合并特效和结算动画。风格选了浅色积木，镜头固定，不用转来转去，能看清数字就行。

[新版在这里](/games/2048-three)，[原版也留着](/2048/index.html)。

![新版初始棋盘](/images/2048-three/initial.png)

## 先拆开游戏逻辑

原来一个方块对象里既有数字、位置，也有 DOM 节点。换成 Three.js 后，这部分得拆开：规则只管数字怎么移动、怎么合并，场景负责把这个过程画出来。

每个方块都有稳定的 `id`，以及 `value`、`row`、`col`。一次移动返回下一份棋盘、移动路径、发生合并的方块和得分：

```ts
export interface Turn {
  tiles: Tile[]
  motions: Motion[]
  merged: number[]
  gain: number
  changed: boolean
}
```

先按移动方向把一行或一列排好，再依次取出数字。两个相邻数字相同时合并，并跳过第二个数字。这样 `[2, 2, 4, 4]` 向左会变成 `[4, 8]`，不会在同一回合把刚生成的 4 再合并一次。

无效移动不产生新方块。有效移动后，从空格中随机选一个位置，以 90% 的概率生成 2，10% 的概率生成 4。

这里多返回了一份移动路径。比如两个 2 合成 4，动画需要知道两个 2 分别从哪里过来，光有最后那个 4 还不够。

## 棋盘换成 Three.js

底座和方块都用了圆角盒子，加上半球光、方向光和阴影，就有了积木的感觉。数字越大，颜色越往暖金色走。

预览时浅色方块有些过亮，后来调低了灯光强度，加了色调映射。这个还是得打开页面看，单看代码不太容易判断。

数字通过 Canvas 绘制后生成纹理，放到方块顶部的小平面上。这样数字会跟随方块移动和缩放，不需要另外维护一套覆盖在画布上的数字坐标。

```ts
const texture = new THREE.CanvasTexture(canvas)
texture.colorSpace = THREE.SRGBColorSpace
const textMaterial = new THREE.MeshBasicMaterial({
  map: texture,
  transparent: true,
  depthWrite: false,
})
```

分数、按钮和结算面板继续用 Vue 写，没必要全塞进 3D 场景里。

## 滑过去，再合并

一回合分成三个阶段：先滑动，再提交合并后的棋盘与分数，最后让合并方块和新方块弹出。

滑动时间设成了 150ms，快一点，不然连续操作会觉得拖。缓动用的是三次缓出：

```ts
mesh?.position.lerpVectors(
  position(m.tile.row, m.tile.col),
  position(m.row, m.col),
  1 - (1 - t) ** 3,
)
```

合并后还有一圈粒子和加分浮字。粒子是页面上的短动画，棋盘上的立体运动由 Three.js 完成。

连按方向键时，动画可能还没结束，下一个操作就来了。现在最多缓存一个方向，等这一回合结束再执行。

还有重开的问题：上一局的异步动画可能还在跑。所以每次重开都更新一个任务编号，旧动画回来时对一下编号，过期就退出，免得把上一局的状态写回来。

## 赢了和输了，都补个动画

第一次合出 2048，方块会抬一下，撒一圈金色粒子，再弹出胜利面板。可以继续玩，往 4096、8192 合；这一局里不会反复弹庆祝。

失败判断要检查是否还有可执行的合并。棋盘填满只是前提；如果相邻位置还有相同数字，游戏仍然可以继续。

失败时底座轻微震动，棋盘淡化，结算卡片展示得分、最高方块、有效步数和是否打破纪录。最高分使用独立的本地存储键；浏览器拒绝存储时，当前游戏仍可正常运行。

## 接回博客，还有些零碎的事

滑动操作只绑定在棋盘区域，棋盘外仍然可以正常滚动。方向键、WASD 和屏幕方向按钮走同一个输入函数。

Three.js 在页面挂载后按需加载，避免静态生成阶段访问浏览器 API。画布尺寸跟随容器变化，像素密度限制在 2，减少高分屏上的渲染开销。无法初始化时，页面提供重试和经典版入口。

页面隐藏时暂停渲染，离开时清理动画循环、事件监听、几何体、材质和纹理。Three.js 的 GPU 资源需要显式释放，官方的[资源清理说明](https://threejs.org/manual/pages/cleanup.html)解释了这里的原因。

系统开启“减少动态效果”时，关闭粒子和震动，缩短棋盘动画。

## 最后检查了一遍

规则部分加了 5 个测试用例，覆盖四个方向、连续合并、生成数字、满盘判断，以及合出 2048 后继续玩。测试、类型检查和静态构建都过了。

浏览器里看了手机宽度和桌面布局，也试了方向按钮、合并计分、胜利后继续和失败重开。检查时发现预设棋盘会在重开后再次加载，已经改成只在首次进入时使用。

键盘的自动化检查遇到了工具超时，实际触屏、“减少动态效果”和 WebGL 启动失败的情况还没逐一测完，先记在这里。

装依赖也折腾了一下。这个项目的 pnpm 版本比较老，和本机默认的 Node 不太合得来。中间还带动了旧依赖的更新，最后恢复了原来的锁文件，只补上 Three.js 需要的包。

从 2019 年的几个 div，变成现在这块立体棋盘，原来的版本也还在。放在一起看，倒是挺适合留个纪念。
